      06 · Method

      How a run works

      1. 01

        Task

        One real task with a single checkable answer. Its hash is committed before any model runs.

      2. 02

        5 models

        Same prompt, same tool schema, same step budget (max 10 tool calls), default sampling settings for each model, listed per model.

      3. 03

        Tools

        Quotes, pools, token data. Every response is frozen at one slot and logged call by call. Before the run, the tool server captures responses for a fixed, published set of arguments (pairs, amounts, pool IDs) at the slot; any call outside that set returns a logged error.

      4. 04

        Check

        The answer is compared to the ground truth from the same snapshot. Method per category is listed in the roadmap.

      5. 05

        Score

        Pass if at most % below the best; any answer above the best fails. Distance is also published in bps, with the trace.

      Fixed rules

      Prompt, tools and pass threshold are versioned in METHODOLOGY.md. A rule change gets its own commit and a note on the site. Answers above the best reachable output count as wrong (hallucinated route).

      Reproducible

      Every run stores the slot, the raw JSON of every tool response, model IDs, prompts and outputs. Re-scoring the stored outputs is deterministic. Rerunning a model replays identical tool responses, but its output may differ because of sampling. The live market cannot be replayed; the snapshot can.

      No cherry-picking

      The run log is append-only in git. Failed or voided runs stay visible with a reason. No reruns of a day: a rerun is a new, separately labelled run. Tasks are committed (hash) before models run.

      No sponsors

      No model team can pay for placement. The project is independent and not affiliated with any model provider.
